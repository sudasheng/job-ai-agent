八、面试官可能问的问题

Q1: 为什么用向量数据库而不是传统数据库做语义检索？
传统数据库（MySQL/ES）做的是关键词匹配，无法理解语义。比如搜"Python后端面试题"，传统数据库只能匹配包含这几个字的文档，搜不到"FastAPI开发考点"这种语义相关的内容。

向量数据库将文本通过 Embedding 模型转为高维向量，通过余弦相似度/欧氏距离做语义匹配。"Python后端面试题"和"FastAPI开发考点"在向量空间中距离很近，能被检索到。

本项目面试场景中，用户输入的岗位描述和题库中的知识点往往不是精确匹配，必须用语义检索。
Q2: ChromaDB 的检索原理是什么？为什么快？
ChromaDB 底层使用 HNSW（Hierarchical Navigable Small World）算法做近似最近邻检索（ANN）。

HNSW 是一个多层图结构：底层包含所有向量节点，上层是稀疏索引用于快速定位。搜索时从顶层开始，逐层向下贪心搜索，最终在底层找到近似最近邻。

时间复杂度 O(log n)，远优于暴力搜索的 O(n)。1万条数据检索延迟 <10ms。代价是需要额外内存存储图结构（约 1.5~2 倍向量内存）。
Q3: 什么是 Embedding？维度越高越好吗？
Embedding 是将文本映射到高维向量空间的过程，语义相似的文本在向量空间中距离近。

维度选择的权衡：维度越高语义表达越精细，但存储和计算成本越高；维度越低速度快、省内存，但可能丢失语义细节。

业界常用维度：384/512（轻量）、768/1024（通用，本项目使用）、1536/3072（高精度）。实际经验：1024 维在大多数中文场景下足够，再高维度收益递减。
Q4: 文本切分策略怎么设计？chunk_size 和 overlap 怎么定？
切分策略直接影响检索质量。

chunk_size：太小（<200）语义不完整，太大（>2000）检索不精准，推荐 500~1500，本项目用 1000。

chunk_overlap：防止关键信息被切断在两个 chunk 边界，推荐 chunk_size 的 10~20%，本项目用 200。

separators：中文场景需要加"。"作为分隔符，优先按段落→句子→空格→字符逐级切分。

本项目岗位 JD 采用结构化拼接（岗位名称+公司+经验+...），再统一切分，保证每个 chunk 包含完整的岗位信息片段。
Q5: 什么是多路检索？为什么需要 Query 改写？
用户输入"3年Python后端，FastAPI、Redis、MySQL"，直接用这句话去检索可能效果不好，因为查询太长语义被稀释，不同角度的信息混在一起。

Query 改写的做法：用 LLM 将用户输入拆分为多个精准查询："Python后端面试题"、"FastAPI面试考点"、"Redis缓存面试题"。每个查询单独检索，结果合并去重。

好处：召回率显著提升（不同角度的结果都能被检索到），结果多样性更好。
Q6: 向量数据库的数据量大了怎么办？如何水平扩展？
ChromaDB 是单机版，数据量到百万级别会遇到瓶颈。

短期优化（不换库）：向量量化（PQ/SQ8）压缩向量减少内存、Metadata 预过滤缩小范围、分 Collection 按类型分集合。

长期方案（换库）：Milvus（分布式，亿级）、pgvector（复用PG）、Qdrant（Rust实现，高性能）。

迁移策略：抽象 VectorStoreManager 接口，底层可切换。LangChain 的 VectorStore 统一 API，换库只需改一行初始化代码。
Q7: 如何评估检索质量？用什么指标？
离线评估：Recall@K（Top-K 中包含正确答案的比例）、MRR（正确答案排名的倒数均值）、NDCG（考虑排名位置的综合评分）。

在线评估：点击率/采纳率、空结果率、延迟 P99。

本项目评估方式：人工抽检（随机取 100 条检查 Top-3 相关性）、A/B 测试（对比有/无 RAG 的面试题质量）、监控 score 分布。
Q8: 本项目 RAG 完整链路是什么？每步的目的？
完整链路：Query 改写 → 多路向量检索 → 去重排序 → Prompt 注入 → LLM 生成

1. Query 改写：用 LLM 拆分多角度检索查询，提升召回率
2. 多路向量检索：每个查询在多个 Collection 中并行搜索
3. 去重排序：同一文档去重后按相似度排序
4. Prompt 注入：Top-K 结果作为上下文注入 Prompt
5. LLM 生成：结合岗位 JD + 检索知识生成专业面试题

好处：LLM 不是凭空出题，而是基于真实题库知识，题目更专业更有针对性。
Q9: ChromaDB 和 ES 做语义检索的区别？
ChromaDB：纯向量相似度检索，语义理解强，部署简单（pip install），适合中小数据量。
Elasticsearch：关键词 + 向量（8.x+），语义能力中等，部署复杂（JVM + 集群），适合大数据量 + 混合查询。

本项目选 ChromaDB：数据量小、纯语义检索场景、无需复杂过滤。如果数据量增长，可考虑 ES 8.x 的 dense_vector + BM25 混合检索。
Q10: Embedding 模型更新后，向量怎么处理？
Embedding 模型更新后，新旧向量不在同一空间，不能直接比较。

方案一（推荐）：全量重索引，用新模型重新生成所有向量。数据量小时成本低。
方案二：双写过渡期，新旧模型同时写入不同 Collection，检索时合并。
方案三：向量转换，训练线性映射矩阵，精度损失大，不推荐。

工程实践：metadata 中记录 embedding_model 和 embedding_version，版本变更时触发重索引。
