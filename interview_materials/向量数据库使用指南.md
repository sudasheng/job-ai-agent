## 一、技术选型

### 1.1 为什么选 ChromaDB？

| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|----------|
| **ChromaDB** | 轻量级、Python原生、无需独立部署、LangChain原生支持 | 不适合超大规模(>1000万条) | 中小项目、快速原型 |
| Milvus | 分布式、高性能、支持亿级数据 | 部署复杂、资源占用大 | 企业级大规模场景 |
| Pinecone | 全托管、免运维 | 付费、数据在外部 | 不想自建、预算充足 |
| pgvector | 复用已有PostgreSQL、支持混合查询 | 向量检索性能不如专用库 | 已有PG、数据量中等 |
| FAISS | Meta开源、极致性能 | 纯库、无服务端、需自建持久化 | 纯检索场景、离线批处理 |

**本项目选择 ChromaDB 的理由：**
- 面试题库数据量小（千级别），ChromaDB 足够
- Python 原生，开发效率高
- 内置持久化，无需额外部署
- LangChain 原生集成，代码简洁

### 1.2 Embedding 模型选型

| 模型 | 维度 | 价格 | 适用场景 |
|------|------|------|----------|
| **千问 text-embedding-v3** | 1024 | 极低（DashScope） | 本项目使用 |
| OpenAI text-embedding-3-small | 1536 | $0.02/1M tokens | 英文为主 |
| BGE-M3 | 1024 | 免费本地部署 | 多语言、离线场景 |
| Jina Embeddings v3 | 1024 | 免费额度 | 多语言、高精度 |

**本项目使用千问的原因：**
- 国内访问快、延迟低
- 中文语义理解优秀
- 价格极低，适合面试场景高频调用

## 二、在本项目中的使用思路

### 2.1 整体 RAG 流程

```
用户输入岗位 JD
    ↓
Query 改写（LLM 生成多角度检索词）
    ↓
多路向量检索（ChromaDB 多集合并行搜索）
    ↓
结果去重 + 按相似度排序
    ↓
Top-K 结果注入 Prompt
    ↓
LLM 生成面试题 / 评分
```

### 2.2 核心代码调用链

```python
# 1. 入口：main_graph.py 中的 _gen_first_question_node
rag_data = await _search_knowledge(job_jd)

# 2. _search_knowledge 调用检索器
retriever = get_retriever()  # MultiPathRetriever 单例
results = await retriever.retrieve(query=job_text, top_k=3)

# 3. MultiPathRetriever 内部流程
#    3.1 Query 改写
rewritten = await self.rewrite_query(query, direction)
#    3.2 多路检索
results = self._vector_store.multi_search(query, collections=..., k_per_collection=top_k)

# 4. VectorStoreManager.multi_search 内部
#    遍历多个 collection，调用 ChromaDB similarity_search_with_score
for col_name in collections:
    results = collection.similarity_search_with_score(query, k=k, filter=filter)

# 5. 结果按 score 排序（分数越低越相似）
all_results.sort(key=lambda x: x["score"])
```

## 四、关键代码详解

### 4.1 VectorStoreManager 核心方法

```python
# app/rag/vector_store.py

class VectorStoreManager:
    def __init__(self):
        # ChromaDB 持久化客户端
        self._client = chromadb.PersistentClient(
            path=persist_dir,
            settings=ChromaSettings(anonymized_telemetry=False),
        )
        self._embeddings = get_embeddings()  # 千问 Embedding

    def get_collection(self, name) -> Chroma:
        """获取或创建集合（惰性创建）"""
        return Chroma(
            client=self._client,
            collection_name=name,
            embedding_function=self._embeddings,
        )

    def search(self, query, k=5, filter=None):
        """向量相似度检索"""
        results = collection.similarity_search_with_score(query, k=k, filter=filter)
        # 返回: [{"content": "...", "metadata": {...}, "score": 0.35}, ...]
        # score 越低越相似（L2 距离）

    def multi_search(self, query, collections, k_per_collection):
        """多路检索 —— 多集合结果合并"""
        for col_name in collections:
            results = self.search(query, k=k_per_collection, collection_name=col_name)
            all_results.extend(results)
        all_results.sort(key=lambda x: x["score"])  # 按相似度排序
```

### 4.2 MultiPathRetriever 多路检索

```python
# app/rag/retriever.py

class MultiPathRetriever:
    async def retrieve(self, query, direction, top_k=5):
        # 1. Query 改写：将用户输入拆分为多个检索视角
        rewritten = await self.rewrite_query(query, direction)
        # 输出: {"rewritten_queries": ["Python后端面试题", "FastAPI考点", "Redis面试"]}

        # 2. 多路检索：每个改写查询搜索多个集合
        for rq in rewritten_queries[:3]:
            results = self._vector_store.multi_search(rq, collections=...)

        # 3. 去重：同一文档只保留最高分
        seen_ids = set()
        for r in results:
            if doc_id not in seen_ids:
                seen_ids.add(doc_id)
                all_results.append(r)

        # 4. 排序截断
        all_results.sort(key=lambda x: x["score"])
        return all_results[:top_k]
```

## 六、优化方向

### 6.1 检索质量优化

| 优化方向 | 具体做法 | 效果 |
|----------|---------|------|
| **Query 改写** | LLM 生成多角度检索词（已实现） | 召回率 +20~30% |
| **重排序（Rerank）** | 检索后用 Cross-Encoder 重排 | 精准率 +15~25% |
| **混合检索** | 向量检索 + BM25 关键词检索 | 召回率 +10~20% |
| **Metadata 过滤** | 按 type/direction/difficulty 预过滤 | 减少噪声、提速 |

### 6.2 性能优化

| 优化方向 | 具体做法 | 效果 |
|----------|---------|------|
| **批量写入** | `add_texts` 批量而非逐条 | 写入速度 x10 |
| **索引类型** | HNSW（默认）→ 调参 ef/ M | 检索精度/速度平衡 |
| **向量量化** | PQ/SQ8 压缩向量 | 内存减半、速度提升 |
| **缓存** | 热门查询结果缓存 | 重复查询 <1ms |

### 6.3 工程优化

| 优化方向 | 具体做法 |
|----------|---------|
| **增量索引** | `is_vectorized` 标记（已实现），只索引新增数据 |
| **异步写入** | 后台任务批量索引，不阻塞主流程 |
| **多租户隔离** | 每用户一个 Collection 或 Metadata 过滤 |
| **监控告警** | 检索延迟、命中率、空结果率监控 |

## 七、面试官可能问的问题 & 回答思路

### Q1: 为什么用向量数据库而不是传统数据库做语义检索？

**回答思路：**
> 传统数据库（MySQL/ES）做的是**关键词匹配**，无法理解语义。比如搜"Python后端面试题"，传统数据库只能匹配包含这几个字的文档，搜不到"FastAPI开发考点"这种语义相关的内容。
>
> 向量数据库的核心是将文本通过 Embedding 模型转为高维向量，通过**余弦相似度/欧氏距离**做语义匹配。这样"Python后端面试题"和"FastAPI开发考点"在向量空间中距离很近，能被检索到。
>
> 本项目面试场景中，用户输入的岗位描述和题库中的知识点往往不是精确匹配，必须用语义检索。

---

### Q2: ChromaDB 的检索原理是什么？为什么快？

**回答思路：**
> ChromaDB 底层使用 **HNSW（Hierarchical Navigable Small World）** 算法做近似最近邻检索（ANN）。
>
> HNSW 是一个多层图结构：
> - 底层包含所有向量节点
> - 上层是稀疏索引，用于快速定位
> - 搜索时从顶层开始，逐层向下贪心搜索，最终在底层找到近似最近邻
>
> 时间复杂度 O(log n)，远优于暴力搜索的 O(n)。1万条数据检索延迟 <10ms。
>
> 代价是需要额外内存存储图结构（约 1.5~2 倍向量内存）。

---

### Q3: 什么是 Embedding？维度越高越好吗？

**回答思路：**
> Embedding 是将文本映射到高维向量空间的过程，语义相似的文本在向量空间中距离近。
>
> 维度选择的权衡：
> - **维度越高**：语义表达越精细，但存储和计算成本越高
> - **维度越低**：速度快、省内存，但可能丢失语义细节
>
> 业界常用维度：
> - 384/512：轻量场景
> - 768/1024：通用场景（本项目使用 1024）
> - 1536/3072：高精度场景
>
> 实际经验：1024 维在大多数中文场景下足够，再高维度收益递减。

---

### Q4: 文本切分策略怎么设计？chunk_size 和 overlap 怎么定？

**回答思路：**
> 切分策略直接影响检索质量：
>
> **chunk_size**：
> - 太小（<200）：语义不完整，检索到的片段缺乏上下文
> - 太大（>2000）：检索不精准，噪声多
> - 推荐 500~1500，本项目用 1000
>
> **chunk_overlap**：
> - 防止关键信息被切断在两个 chunk 边界
> - 推荐 chunk_size 的 10~20%，本项目用 200
>
> **separators**：
> - 中文场景需要加 `"。"` 作为分隔符
> - 优先按段落 → 句子 → 空格 → 字符逐级切分
>
> 本项目岗位 JD 采用结构化拼接（岗位名称+公司+经验+...），再统一切分，保证每个 chunk 包含完整的岗位信息片段。

---

### Q5: 什么是多路检索（Multi-Path Retrieval）？为什么需要 Query 改写？

**回答思路：**
> 用户输入"3年Python后端，FastAPI、Redis、MySQL"，直接用这句话去检索可能效果不好，因为：
> 1. 查询太长，语义被稀释
> 2. 不同角度的信息混在一起
>
> **Query 改写**的做法：
> - 用 LLM 将用户输入拆分为多个精准查询：
>   - "Python后端面试题"
>   - "FastAPI面试考点"
>   - "Redis缓存面试题"
> - 每个查询单独检索，结果合并去重
>
> **好处**：
> - 召回率显著提升（不同角度的结果都能被检索到）
> - 结果多样性更好
>
> 本项目用 DeepSeek 做 Query 改写，成本极低。

---

### Q6: 向量数据库的数据量大了怎么办？如何做水平扩展？

**回答思路：**
> ChromaDB 是单机版，数据量到百万级别会遇到瓶颈。扩展方案：
>
> **短期优化（不换库）：**
> - 向量量化（PQ/SQ8）：压缩向量，减少内存
> - Metadata 预过滤：先按条件缩小范围再检索
> - 分 Collection：按方向/类型分集合
>
> **长期方案（换库）：**
> - **Milvus**：分布式架构，支持亿级数据，K8s 部署
> - **pgvector**：复用已有 PostgreSQL，数据量中等时够用
> - **Qdrant**：Rust 实现，性能优秀，支持分布式
>
> **迁移策略**：
> - 抽象 VectorStoreManager 接口，底层可切换
> - LangChain 的 VectorStore 统一 API，换库只需改一行初始化代码

### Q7: 如何评估检索质量？用什么指标？

**回答思路：**
> 检索质量评估指标：
>
> **离线评估：**
> - **Recall@K**：Top-K 结果中包含正确答案的比例
> - **MRR（Mean Reciprocal Rank）**：正确答案排名的倒数均值
> - **NDCG**：考虑排名位置的综合评分
>
> **在线评估：**
> - **点击率/采纳率**：用户是否使用了检索结果
> - **空结果率**：检索无结果的比例
> - **延迟 P99**：99 分位延迟
>
> **本项目评估方式：**
> - 人工抽检：随机取 100 条岗位，检查 Top-3 检索结果是否相关
> - A/B 测试：对比有 RAG 和无 RAG 的面试题质量
> - 监控：记录每次检索的 score 分布，异常低分告警

---

### Q8: 本项目中 RAG 的完整链路是什么？每一步的目的是什么？

**回答思路：**
> 完整链路：**Query 改写 → 多路向量检索 → 去重排序 → Prompt 注入 → LLM 生成**
>
> 1. **Query 改写**：用 LLM 将用户输入拆分为多个精准检索查询，提升召回率
> 2. **多路向量检索**：每个查询在多个 Collection 中并行搜索，获取语义相关文档
> 3. **去重排序**：同一文档可能被多个查询命中，去重后按相似度排序
> 4. **Prompt 注入**：将 Top-K 结果作为上下文注入面试题生成 Prompt
> 5. **LLM 生成**：DeepSeek 结合岗位 JD + 检索知识，生成专业面试题
>
> 这样做的好处是：LLM 不是凭空出题，而是基于真实题库知识，题目更专业、更有针对性。

---

### Q9: ChromaDB 和 ES（Elasticsearch）做语义检索的区别？

**回答思路：**
> | 维度 | ChromaDB | Elasticsearch |
> |------|----------|---------------|
> | 检索方式 | 纯向量相似度 | 关键词 + 向量（8.x+） |
> | 语义理解 | 强（依赖 Embedding） | 弱（BM25）/ 中等（dense_vector） |
> | 部署复杂度 | 低（pip install） | 高（JVM + 集群） |
> | 数据规模 | 中小（<100万） | 大（亿级） |
> | 混合查询 | 不支持 | 支持（向量+过滤+聚合） |
>
> **本项目选 ChromaDB 的原因**：数据量小、纯语义检索场景、无需复杂过滤。
>
> **如果数据量增长**：可以考虑 ES 8.x 的 dense_vector + BM25 混合检索，兼顾语义和关键词匹配。

---

### Q10: 如何处理 Embedding 模型的更新和向量重索引？

**回答思路：**
> Embedding 模型更新后，新旧向量不在同一空间，不能直接比较。处理方案：
>
> **方案一：全量重索引（推荐）**
> - 用新模型重新生成所有向量
> - 数据量小（千级别）时成本低
> - 本项目适合此方案
>
> **方案二：双写过渡期**
> - 新旧模型同时写入不同 Collection
> - 检索时合并结果
> - 过渡期结束后删除旧 Collection
>
> **方案三：向量转换**
> - 训练线性映射矩阵，将旧向量转到新空间
> - 精度损失大，不推荐
>
> **工程实践**：
> - 在 metadata 中记录 `embedding_model` 和 `embedding_version`
> - 版本变更时触发重索引任务
> - 本项目 `is_vectorized` 标记可复用，重置为 False 即触发重索引

### 项目介绍（30 秒版）

> "我的项目是一个 AI 面试 Agent，使用 LangGraph 状态机管理面试流程，ReAct Agent 自主采集岗位信息。核心 RAG 模块基于 ChromaDB 向量数据库存储面试题库，通过千问 Embedding 模型将文本转为 1024 维向量。检索时先用 LLM 做 Query 改写生成多角度检索词，再从多个 Collection 中并行检索，结果去重排序后注入 Prompt，让 LLM 生成岗位定制化的面试题。"

### 技术深度追问准备

**"为什么不用 FAISS？"**
> FAISS 是纯检索库，没有持久化、没有服务端，需要自己管理索引文件。ChromaDB 内置持久化和客户端，开发效率更高。本项目数据量小，ChromaDB 性能完全够用。

**"score 是什么含义？怎么判断结果好不好？"**
> ChromaDB 默认用 L2（欧氏距离），score 越小越相似。一般 score < 0.5 表示高度相关，0.5~1.0 中等相关，>1.0 可能不相关。但不同 Embedding 模型的 score 分布不同，需要实际测试校准阈值。

**"如果检索结果都不相关怎么办？"**
> 1. 检查 Query 改写是否生效
> 2. 降低相似度阈值，扩大召回范围
> 3. 兜底策略：用 LLM 自身知识出题（已实现，`_search_knowledge` 异常时返回默认提示）
> 4. 长期：增加 Rerank 模型二次排序
